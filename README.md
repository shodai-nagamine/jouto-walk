# 城東小あるき — PLATEAU那覇を歩く

**▶ 遊ぶ: <https://shodai-nagamine.github.io/jouto-walk/>**（スマホ可）

<img src="jouto-walk-qr.png" width="180" alt="公開URLのQRコード">


那覇市 **城東小学校** を中心とした 1km 四方を、国土交通省 PLATEAU の実測データ
（建物 CityGML LOD1 ＋ 地形 DEM）から起こして歩き回れるようにした Three.js の一人称ゲーム。
街に散らばった **10体のシーサー** を探して保護するのが目的。

- 建物 **1,905棟**（実在の footprint と高さ）
- 地形 **201×201 の 5m 格子**（標高 82.7〜154.0m の起伏をそのまま再現）
- 城東小の地表標高 115m。首里寄りの高台という土地の性格が歩くと分かる

## 起動

ローカルで動かす場合:

```bash
python3 -m http.server 8945 --directory ~/dev/apps/jouto-walk/public
```

<http://localhost:8945> を開く。ビルド不要（Three.js は `public/lib/` に同梱）。

## 公開

`main` に push すると GitHub Actions（`.github/workflows/pages.yml`）が
`public/` を GitHub Pages へ配信する。ビルド手順は無く、成果物をそのまま上げるだけ。
配信サイズは約 1.3MB（`world.json` は gzip で 0.2MB）。

### デプロイでハマった点（2026-08-06）

- `concurrency` は **`cancel-in-progress: false`**。`true` だと進行中のデプロイを
  打ち切って Pages 側が `Deployment cancelled` になり、上げ直しても反映されない
- **失敗したジョブを `gh run rerun --failed` で再実行しない**。同じ run に
  `github-pages` という名前のアーティファクトが2つでき、
  `Multiple artifacts named "github-pages"` で必ず落ちる。新しい run を投げること
  （`gh workflow run pages.yml` か、新規 push）
- `deploy-pages` の `timeout` は **10分が上限**（それ以上を書いても丸められる）。
  Pages 側の配信がこれを超えると **ジョブは failure になるが、配信は後から完了して
  公開される**。赤いバツを見たら、まず本番の中身を確認する:

  ```bash
  curl -s https://shodai-nagamine.github.io/jouto-walk/main.js | grep -c setFly
  ```

## ワールドデータの作り直し

`public/data/world.json` は下のコマンドで生成する。CityGML と DEM の原本、および
パーサ資産（`gml_to_schematic.py` / `dem_grid.py`）は `~/dev/tools/blender-mcp/data/naha/` にある。

```bash
~/dev/tools/blender-mcp/.venv/bin/python tools/build_world.py \
  --center 26.2233 127.7322 --size 1000 \
  --gml 39272568.gml 39272578.gml \
  --dem 392725_dem_55.gml \
  --tran 39272568_tran.gml 39272578_tran.gml \
  --rail naha_railway.geojson --stations naha_station.czml \
  --bus naha_bus_osm.json --osm-named naha_named_osm.json \
  --bus-routes naha_busroutes_osm.json --signals naha_signals_osm.json \
  --footways naha_footways_osm.json \
  --parks naha_parks_osm.json \
  --out public/data/world.json
```

バス停・地名辞書・信号・歩道・公園は OpenStreetMap から Overpass API で取る:

```bash
python3 tools/fetch_osm.py
```

**5 本とも同じ範囲**（`lat 26.182〜26.246 / lon 127.638〜127.742`）で取る。これは
corridor 全体（那覇空港〜石嶺）に、タイルが中心から ±500m はみ出すぶんの余白を
足したもの。`build_world.py` が各タイルの bbox で切るので、広いぶんには害がない。
投げたクエリは `naha_*_osm.query.txt` に写しが残る。

- **範囲を狭めない**こと。以前はバス停・地名・信号・歩道だけが城東小まわりの
  1km 四方（`26.2188,127.7272,26.2278,127.7372`）で、隣のタイル `t_-1_0` が
  信号 0 基・バス停 0 基・歩道 7 本になっていた
- 1 発で 504 が返るときのために、`fetch_osm.py` は緯度で帯に割って取り直し、
  `(type, id)` で重複を除いて結合する（帯の境界で地物が落ちないよう 220m 重ねる）。
  実測ではこの範囲なら 5 本とも 1 発で通り、合計 10MB / 26 秒だった
- 公園だけは `["name"]` で絞らない。那覇の街区公園と校庭は半数以上が無名で、
  名前で絞ると見た目に一番効く大きなグラウンドが軒並み落ちるため
  （この 1km 四方でも 4 面 → 12 面に増える）

タイトル画面の「開発ログ」は git 履歴から作る。手書きの記録ではないので
書き忘れも盛りもない。GitHub Actions が push のたびに作り直すため、
ワークフローの checkout は `fetch-depth: 0`（全履歴）にしてある:

```bash
python3 tools/build_changelog.py --out public/data/changelog.json
```

市議会の言及は world.json を作ったあとに別途生成する（Postgres が要る）:

```bash
python3 tools/link_council.py --world public/data/world.json --out public/data/council.json
```

### 市議会リンクの作り方

1. **地名辞書**: CityGML の `gml:name` はタイルあたり 4〜7 件しかないので、
   OSM の名前付き地物（`--osm-named`、196 件）で厚くする。これで
   「石嶺市営住宅」「石嶺公民館」「市道城東城北線」など議事録に出る名前が入る
2. **絞り込み**: 議会が議題にするのは公共施設と道路なので、OSM のタグか
   名前のキーワードで**公共施設だけに限る**。これをやらないと
   「ほっともっと」が金芽米の話に、「コープ」が労働者協同組合ワーカーズコープに
   当たるといった誤検出が出る（実際に出た）
3. **並び順**: 発言者不明（32 件ある）と議長の議事進行を後ろへ回し、
   議員の質疑と執行部の答弁を先に出す

現在は **4 地点 / 8 発言**（城東小学校・石嶺中学校・石嶺公民館・石嶺市営住宅）。
収録が那覇市議会の令和 8 年 2 月定例会 13 日分なので、会議録を増やせばそのまま増える。

- `--center` は緯度経度。別の場所にすれば那覇市内のどこでも作れる（該当メッシュの GML が要る）
- 城東小 26.2233,127.7322 は 3次メッシュ `39272568`。1km 四方だと北隣の `39272578` も必要
- DEM は `_55` 象限のみが該当（`_50` は範囲外で 0 点になる）
- `--tran` は交通（道路）モデル。省略しても動くが、道路は密度場からの推定のみになる
- `--rail` / `--stations` はゆいレール。CityGML ではなく GeoJSON と CZML（PLATEAU の
  RELATED データセット `d_47201_railway` / `d_47201_station`）を使う

## タイル化（那覇空港〜石嶺の全線・37 タイル）

世界をモノレール沿いに広げるため、**1km 格子のタイル**に分ける。四角く広げると
地面テクスチャが破綻する（0.5m/px のまま 3km 四方にすると 6144px＝3,770 万ピクセルを
素の JS ループで焼くことになる）が、**タイルごとに今と同じ 1km 世界を作れば
既存のパイプラインがそのまま使える**。

- `--origin LAT LON` で**全タイル共通の原点**を指定する。緯度経度→メートルの換算を
  原点の緯度で統一しないと、タイルごとに縮尺がずれて継ぎ目が出る
- 各タイルの `meta.offset` に、原点から見た中心位置（m）が入る
- **地形は余白ぶん広く作ってから切り出す**（`DEM_PAD = 20` セル＝100m）。
  `fill_missing` のラプラス緩和は外周を `mode="edge"`（勾配ゼロ）で閉じるので、
  タイルの縁をそのまま境界にすると、隣り合うタイルが互いに自分の縁を平らと
  みなして標高が食い違う。**実測で最大 2.5m の段差**が出た（タイル内側の
  隣接点の差は最大 0.36m なので、明らかに継ぎ目だけの異常）。余白を入れると
  共有する縁の列が**ぴったり 0.000m 一致**する
- OSM は**タイルをまとめて覆う 1 回のクエリ**で取り、同じファイルを
  `--bus` `--osm-named` `--signals` `--footways` に渡す。
  各パーサはタグを見て自分の担当だけを拾う（この絞りが無いと
  「市道○○線」が歩道として描かれる）
- **建物・道路の GML はタイルより広く渡してよい**。パーサが bbox で切るので、
  重なる 3 次メッシュを全部並べておけば取りこぼさない

### タイルの作り方（全線 37 枚）

素材（PLATEAU の CityGML）を取ってから、まとめて回す:

```bash
python3 tools/fetch_citygml.py     # 不足している建物・交通モデルを落とす
python3 tools/build_tiles.py       # corridor 全体を 1km タイルに切って生成
python3 tools/build_tile_index.py  # index.json を作り直す
```

那覇空港〜石嶺を路線±600m で覆うと **37 タイル・19MB**（生成 75 秒）。
公開物に含めてある（GitHub Pages のソフトリミット 1GB に対して十分小さい）。

- **CityGML の実ダウンロードは 49MB**（建物 34 枚 + 交通 41 枚、gzip 後）。
  手元の展開済みファイル 1 枚 22MB から外挿すると 880MB に見えるが、
  回廊の大半は海・空港・低密度で中身が薄い。展開後で 562MB
- 3 次メッシュ 1 枚は約 1.15km × 0.93km なので、1km 四方のタイルはたいてい
  **4 枚にまたがる**。`build_tiles.py` は余白 150m ぶん広くメッシュを拾う
- 海域などで**元々存在しないメッシュがある**（16 件）。404 は飛ばしてよい
- **地形 DEM は 2 次メッシュ 392725 が 4 分割**（`_00` / `_05` / `_50` / `_55`）で
  配られている。**4 枚とも渡すこと**。`_50` / `_55` だけだと那覇空港・小禄の側が
  「範囲内に点なし」になり、**標高 0.0〜0.0m の平らなタイルが 7 枚**できた

### タイル登録簿（index.json）

`public/data/tiles/index.json` に「この世界にどのタイルがあるか」を持つ。
`tools/build_tile_index.py` が置いてあるファイルから作る（タイルを増やしたら流し直す）。

これは **いま読み込んでいるタイルとは別物**で、歩き回っても変わらない。

- **歩ける範囲**と**ミニマップの縮尺**はこちらで決める。読み込みに追従させると、
  歩くたびに地図の縮尺が変わって現在地が掴めなくなる
- **シーサーの分母**もこちらで決める。タイルを読むたびに増えると
  「ぜんぶ保護する」の目標が動いてしまう。**全線で 30 体**（`N_SEESAA`）を
  タイルに均等に配る（`SEESAA_QUOTA`）。タイルごとに 10 体だと 37 タイルで
  370 体になり集めきれない

### ミニマップはプレイヤー追従

世界が 10km × 7km に広がったので、全体を 1 枚に収めると **53m/px** になり
建物 1 棟が 0.28px になって潰れる（1 タイル世界のときは 5.3m/px だった）。
**プレイヤーの周り 1.2km だけを一定の縮尺で見せる**。下地はタイルごとに
256px（3.9m/px）で焼いておき、毎フレーム窓の位置に貼り直す。

### 距離による読み込み／破棄

`syncTiles()` が tick から 32 フレームに 1 回呼ばれ、プレイヤーの位置に合わせて
タイルを足し引きする。`?tiles=0,0;-1,0` を付けた場合は足し引きしない（検証用）。

- **読む 700m / 捨てる 1100m**（タイルの四角までの距離）。700 で読むと、タイルの
  真ん中に立ったとき四方の隣（距離 500）が入り、斜めの隣（707）は入らない。
  1100 で捨てると持つのは最大 3×3＝9 枚（約 6MB・2 万棟）に収まる。
  差の 400m は歩き 4.6m/s で 87 秒ぶんあるので、境目で行ったり来たりしても
  読み直しにはならない
- **タイルをまたぐもの**（桁・駅・バス・受け皿・地図の下地）は `rebuildDerived()` で
  そのつど組み直す。列車とバスの走行位置は**距離ではなく世界座標**で引き継ぐ
  （線形が 1,119m ↔ 2,495m と伸び縮みするので、距離のまま渡すと数百m飛ぶ。
  実測で引き継ぎ後のずれは 1.3m 以内）
- **タイルごとの擬似乱数**（鍵から種を作る）を使う。全タイル共通の乱数だと、
  同じタイルに戻るたびに木や遊具の位置が変わる（**実測で固体の数が
  2630→2640→2639 と揺れた**）。いまは 4 往復しても同じ街に戻る
- **シーサーはタイルに属さない**。専用の入れ物（`seesaaGroup`）に置き、捨てない。
  一度置いたタイルは `seesaaDone` に覚える（これが無いと再訪のたびに 10 体増えた）。
  歩道が消えた個体はその場に立たせ、タイルが戻ったら**いま立っている場所の
  いちばん近い歩道**へ戻す（遠くの歩道へ乗せ直すと、離れて居たはずの 1 体が
  プレイヤーの目の前へ湧く）
- 破棄で外すもの: `t.group`（描画・`disposeTree` で GPU 側も解放）、
  `bmap`/`rmap`（`hashRemove`）、`bstore`/`rstore`/`busSigns`/`shopSigns`/`signals`
  （`tile` 印で filter）、`walkLines`（`dropWalkLines`）

実測（タイル 2 枚を 4 往復させて）: 当たり判定は総当たりと 30,628 点で不一致 0、
ハッシュに死んだレコード 0、店 137 軒の出入りで漏れ 0、フィナーレ後に
`scene.children` が基準値に戻る。

### 地面テクスチャはフレームをまたいで焼く

タイル 1 枚を一気に焼くと **2.1 秒フリーズした**（実測）。内訳は
`groundTexture()` の画素ループ 744ms ／ `getImageData` × 6 枚 519ms ／
14m ぼかし 144ms ／ 道路・歩道・公園の canvas 81ms ／ 敷地 22ms。

上位 2 つ（全体の 76%）は**横帯に切れる**ので、64 行ずつ `bakes` の行列に積んで
tick から 10ms ずつ進める。焼き上がるまでは平らな色で見せる
（途中の canvas は建物が白抜きの白黒なので貼れない）。

- **最悪の 1 フレーム 2,145ms → 454ms**。焼きは中央値 17ms・2 番目以降の最悪 34ms
- 最初の 1 回だけ 150ms かかる。新しい canvas の初回読み出し（GPU → CPU）の
  ぶんで、帯を細かくしても減らない
- 残る 454ms は `addRoads` / `addBuildings` / 6 枚の canvas / 地形メッシュに
  ばらけていて、突出した山は無い
- **ぼかしを 1/4 解像度でやる案は測って捨てた**。等倍 12ms・1/4 も 12ms で
  差が出ない（初回に見えた 144ms はウォームアップだった）

## 首里城の石垣（2026-08-08）

首里城の姿を決めているのは正殿より **石垣（城郭）**。PLATEAU の那覇は建物 LOD1 のみで
石垣は「建物」ではないので入っておらず、公園の中に低い箱が数棟建つだけだった。
OSM に `barrier=wall` として線形が入っているので、そこから起こす。

- 取得は `tools/fetch_osm.py shurijo`。**範囲を首里城まわりに絞る**
  （`BBOX_OVERRIDE`）。`barrier=wall` を回廊全体で取ると市中のブロック塀を
  何千本も拾う。58 本 / 160 区間 / 総延長 1,053m、4 タイルにまたがる
- **OSM の石垣は高さを持たない**（height / ele のタグは 1 件も無い）。地形から起こす
- 高さの取り方が要点。線に沿った半径で地形の最大値を取る方式では **最大 5.6m**
  にしかならなかった。PLATEAU の DEM は 5m 格子なので、擁壁の段差が 2〜3 セルに
  均されて線上には現れない。**線に直交して左右 9m を測り、その段差を高さにする**と
  最大 9.8m・中央 1.8m になり、実際の首里城の高石垣（10〜14m）と釣り合う
- 天端は移動平均でならす（石垣の天端は水平に近く、ならさないと段々になる）。
  高さ方向の UV は **足元を 0** にする。天端を 0 にすると地面の起伏で目地が波打つ
- 質感は手続き生成の**相方積み**（琉球石灰岩を多角形に加工して噛ませる積み方）。
  格子を大きく揺らして目地を通さない。細かい格子だと本土の布積みに見える
- 各区間を `addSolid` で固体にする（抜けられては困る）。実測で天端と地表の差は最大 7.0m

## 首里城の建物（2026-08-08）

石垣に続いて、城内の建物を OSM の輪郭から起こす。**建てるのは 2019年10月の火災で
焼失する前の姿**（平成の復元）。OSM の輪郭も PLATEAU の計測もその時点のものなので、
数字が突き合わせられるのがこの選択の理由。

- OSM から `正殿 / 北殿 / 南殿・番所 / 奉神門 / 広福門` の輪郭を取る（`--walls` と
  同じ `naha_shurijo_osm.json`）。**PLATEAU の LOD1 の箱は重心が城内建物の輪郭に
  入るものを除外する**（駅舎と同じ扱い。残すと自前の正殿の中に白い箱が刺さる）
- **OSM の輪郭は広い**。正殿は 50.4×24.0m / 831m2 だが、復元設計は
  桁行下層 28.749m × 梁間下層 21.257m（約611m2）。測っているものが違うので、
  **位置と向きだけ OSM から取り、建物の寸法は設計の数字に合わせる**
- 正殿の造形は Antigravity(agy) に契約を渡して書かせた（シーサーと同じやり方）。
  契約: 原点=底面の中心 / 正面=-Z / 28.75×21.26×18.0m / 基本形状のみ /
  Math.random 禁止 / 120メッシュ以内 / MeshLambertMaterial のみ。
  入れるもの: 二重三階の入母屋・唐破風の向拝・赤瓦・朱塗り・大龍柱2本・
  龍頭棟飾・正面の石階段。**機械的な契約は違反ゼロ**（55メッシュ）

### 実機で見て直した3点（数値では出ない）

- **丸瓦が屋根を突き抜けて櫛のように飛び出していた**。長さ10〜15mの円柱を
  屋根面に並べる作りで、勾配に沿っていなかった。屋根の勾配に合わせ直すより、
  この縮尺では平らな赤瓦面のままの方が正しく見えるので落とした
- **脇殿が赤いスラブに見えた**。実測の総高からそのまま壁を立てていたため。
  琉球の建物は**壁が低く屋根が深い**。壁を 4〜5m に下げ、屋根の高さを
  `min(w,d)*0.22` から `*0.52`、軒の出を 1.6m から 2.4m にし、白漆喰の腰壁を足した
- **正殿が御庭に背を向けていた**。輪郭の主軸から向きを取っていたため、唐破風も
  大龍柱も裏側だった。**御庭の正面にある奉神門を狙う**ようにした
  （造形の正面は -Z なので `yaw = atan2(-Δx, -Δz)`）

## 直した不具合（同じ罠を踏まないための記録）

- **DEM を複数枚渡すとタイルの継ぎ目に段差が出た**（2026-08-08 修正）。
  `build_world.py` が **DEM ファイルごとに穴埋めしてから `np.maximum` で重ねて**
  いたため、片方の外挿値がもう片方の実測値を上回った所で外挿が勝っていた。
  DEM が 1 枚しか効かない城東小タイルでは無害だったが、4 分割の境目をまたぐ
  タイルで **継ぎ目に 6.74m の段差**（タイル内側の最大は 0.47m）。
  - 直し方: **点群を全ファイルぶん先に足してから 1 回だけ穴埋めする**。
    継ぎ目の最大 6.74m → **0.561m**（内側 350 本の最大 0.967m・中央値 0.351m を
    下回るので判別できない）。DEM 1 枚のタイルは差 0.0000m で変わらない

- **低地に立つと視界が灰色に覆われた**（2026-08-08 修正）。タイルの外側の
  「受け皿」を **平均標高の水平な円盤**（`CircleGeometry(4000)` を
  `(minZ + maxZ) / 2 - 6` ＝ 112.3m に水平配置）で敷いていたため、
  それより低い場所に立つと**円盤の裏側が空を覆っていた**。
  この 1km 四方は標高 82.7〜154.0m なので低い側の街区がまるごと該当し、
  **歩道網の 41%・シーサー 10 体中 4 体**がその中にいた。
  「全部保護する」遊びそのものが壊れていたことになる。
  - 直し方: 外周を 20m 刻みで拾い、**各点の標高そのままで外へ 1500m 引き伸ばす帯**に
    した。角は隣り合う辺の法線を平均したマイターで隙間なく広がる
  - **受け皿に `receiveShadow` を付けない**こと。影カメラは ±105m しかないので、
    その外側が真っ黒に落ちる
- **空に黒い穴が開いた**（2026-08-08 修正）。空ドームは半径 2000m で原点固定
  だったので、原点から離れるほど反対側が遠のき、**カメラの far（2600m）で切れる**。
  1 タイルでは端でぎりぎり収まっていたが、**2 タイルで x=-1500 に立つと反対側は
  3500m** になり必ず露出する。
  - 直し方: 毎フレームプレイヤーの真上へ運ぶ。あわせて階調を**ワールド座標ではなく
    ドーム内のローカル座標**から取るよう頂点シェーダを変えた
    （ワールド座標のままドームを動かすと階調が傾く）

## 実装のポイント

- **建物**: 全 1,905 棟を 1 つの BufferGeometry に詰めてドローコール 1 回。壁と屋根を
  `addGroup` で 2 マテリアルに分け、壁だけ procedural な窓テクスチャを貼る。UV の横は
  外周の累積距離、縦はその建物の地面からの高さなので、棟をまたいでも階が揃う
- **道路**: PLATEAU 交通モデル（tran LOD1）の道路「面」894 枚。中心線ではなく実際の
  路面形状が入っている（高さは一律 0 なので平面として扱い、地面テクスチャに焼く）。
  1.8m ぼかした版を路肩の帯に使う
- **地面**: 上の道路を最優先で塗り、それ以外は建物 footprint を太らせた「敷地」と、
  14m ぼかした密度場から 敷地／路肩／緑地 を連続補間で塗り分ける。tran に入らない
  私道・路地は密度から弱く（係数 0.5）推定して補う。2048px（0.5m/px）なので足元用に
  細かいノイズを `onBeforeCompile` で乗算している
- **モノレール**: 沖縄都市モノレール（ゆいレール）。線形は **1本 1,025m**。
  元データは路線が細切れの feature で入っているので、**先に端点で繋いでから**
  ワールドで切る（繋がないと 813m/82m/130m の断片になり、列車が短い往復をする）。
  線形データは国土数値情報由来の
  **2D 中心線で高さを持たない**ので、跨座式の高架らしく「地形＋10.5m」を移動平均で
  ならして桁を通し、26m ごとに橋脚を降ろしている（橋脚は InstancedMesh で 1 ドローコール）。
  桁は角断面のリボンとして自前で張る。車両 2 両が線形を往復する（端で消えないように
  ワープではなく折り返し）
- **駅とホーム**: 石嶺駅がワールド内（中心から南西 約 510m）。**ホーム床は桁の高さから
  自動で決まる**（桁中心 −0.7m ＝ 車両の床。実測で地上 106.3m に対し床 114.9m）。
  地上から 19 段の階段で上がれる。
  - PLATEAU の駅舎（17×53m・天端 120.6m）は**中身のない箱**なので、そのままだと
    ホームと階段が壁の中に閉じ込められて一歩も動けない。**駅を含む建物は描画にも
    当たり判定にも入れず**、自前のホーム・上屋・階段で置き換えている
  - 階段が昇れるのは `blocked()` に **STEP（0.55m）の段差許容**を入れたから。
    ホームも階段も `addSolid()` で建物と同じ footprint＋天端として登録するだけでよい
  - 列車が走る線形は**駅のある線形**を選ぶ。長さで選ぶと駅が別の線形に乗っていて
    永久に停まらないことがある（実際に踏んだ）
- **市議会の言及**: `tools/link_council.py` が
  [okinawa-civic-api](https://github.com/shodai-nagamine) の Postgres（那覇市議会
  会議録 9,749 発言）を、ワールド内の施設名で全文検索して地点に結びつける。
  16m 以内に近づくとパネルが出て、**発言者・日付・抜粋・原文リンク**が読める
  （同じ地点に複数あるときは `Q` かパネルのタップで送る）
- **モノレールに乗れる**: 石嶺駅で列車は 9 秒停まる。ホーム上で列車に近づくと乗れる。
  **高さも判定に入れている**ので、高架の下の地上からは乗り込めない。
  降りるとホーム側に降ろされる
- **バスに乗れる**: バス停に停まっているバスへ 6.5m 以内に近づくと乗れる（`E` かボタン）。
  乗車中は移動入力を切って座席（左の窓側、床から 2.15m）へ貼り付け、**見回しだけ自由**。
  バスの更新はプレイヤーより**先**に回す（後だと 1 フレーム遅れて座席がずれる）。
  そばに人が居るバス停では停車時間を 2.2 秒 → 7 秒に延ばして乗る余裕をつくる。
  降車は進行方向の右側（歩道側）に降ろし、塞がっていたら候補を順に試す
- **走るバス**: 経路は OSM のバス路線リレーション（**那覇バスの実系統**）。
  この 1km 四方には 23 系統が通っていて、そのうち世界内を長く走る 4 本
  （94 首里駅琉大快速線 / 346 那覇西原線 / 19 首里駅循環線 / 8 首里城下町線）を採用。
  リレーションのメンバー way は向きが揃っていないので端点の近さで反転させながら繋ぎ、
  ワールドで切って**いちばん長く連続する区間**だけを使う。
  経路上でバス停に近づく地点を先に拾っておき、そこで 2.2 秒停まる。
  **時刻表は持っていないので発車タイミングは任意**（GTFS が手に入れば差し替えられる）
- **信号**: OSM の信号ノード **55 基**（車両用 26／歩行者用 29）を、**交差点 11 箇所**に
  束ねてある。交差点の中心から見た向きで東西（axis 0）と南北（axis 1）に振り分け、
  直交する系統が交互に青になる（同時に青にならないことと、全赤の間があることを検証済み）。
  交差点ごとに位相をずらしてあるので街全体が一斉には変わらない。
  灯火は 165 個を 1 つの InstancedMesh に入れて **per-instance color を書き換えるだけ**
  （0.15 秒ごと）。並びは**運転者から見て左から青・黄・赤**（日本の並び。灯器は
  交差点の中心を向いているので、その視点がそのまま運転者の視点になる）。
  歩行者用は上が赤、下が青
- **バスは赤で止まる**: 各路線の経路上で信号に差しかかる地点を先に拾い、進行方向から
  見る系統（東西か南北か）も決めておく。停止線の 3.5m 手前で青以外なら進まない
- **歩道と車道の区別**: PLATEAU の交通モデルは那覇では **LOD1 のみ**で
  `TrafficArea` / `AuxiliaryTrafficArea` を持たない = **歩道と車道の区別が無い**
  （手元の tran GML を grep して 0 件を確認）。そこで歩行者系は OSM から取る。
  歩道 166・横断歩道 50・階段 27・小径 18。歩道は 2.6m 幅の明るい舗装として
  車道の上に描き、**横断歩道は白い縞**として最後に重ねる（縞は歩行者の進む向きと
  平行な帯なので、way に沿う線を左右にずらして引く）。
  路面を横断方向にサンプルすると明暗が 6 回切り替わることを確認済み
- **店舗**: OSM の名前付き地物から店舗系 48 件を拾い、**食／買／医／金／学／公／他**の
  7 分類に色分けした看板を出す（営業時間があれば併記）。表示は **62m 以内だけ**
- **入口**: OSM の地物は建物の重心あたりに落ちるので、**48 件中 41 件は建物の輪郭の
  内側**にある。そのまま看板を出すと `supportY()` が屋根の天端を返し、**40 件が
  屋根の上**に浮いた（実測）。街の側から入口が見えないので、`findDoor()` が
  **外壁のどの辺が街に開いているか**を決めて扉を付ける。
  - 辺ごとに外向きの法線側 1.4m の点を採り、**道路の上なら +40 点**、
    そこから建物までの距離 ×2、辺の長さ ×0.25 で採点して最良の辺を選ぶ。
    法線の向きは「その点がリングの内側でないほう」で決める（リングの回り方に依存しない）
  - 結果は **48 件すべて扉が地表・正面に立てる**、うち 47 件が外壁に付き、
    29 件が道路に面する。屋根の上の看板は **40 件 → 0 件**
  - 扉一式（沓摺・枠・扉・取っ手・庇）は部品ごとに **InstancedMesh 5 つ**に畳む。
    1 軒 1 オブジェクトだと 48 軒で 300 近いドローコールになる
  - 庇は分類の色。平屋より低い建物では扉が屋根を突き抜けるので、
    `(天端 - 地表) / 3.2` で縮める（この 1km 四方では 1 件が該当）
- **店の中に入れる**: 扉に **6m 以内**まで近づくと `入る [E]`。分類ごとに什器を
  変えた部屋へ移る（食＝テーブルと厨房カウンター／買＝3 段の陳列棚とレジ／
  医＝受付と長椅子／金＝窓口と ATM／学＝机の列と白板／公＝管理棟／他＝汎用）。
  - **PLATEAU の LOD1 には店内が無い**。建物は足元の輪郭を高さぶん押し出した箱で、
    床も内部も 1 階の店舗区画も持たない。実測から店内を起こすことは原理的に
    できないので、**外は本物・中は作り物**と割り切って手続き的に建てている
  - 部屋は街から **8km 離した「舞台」**（`STAGE`）に建てて、そこへ移動する。
    街の真上に建てると `supportY()` が「footprint に入っていれば天端に立たせる」
    仕組みなので、**その真下の路上まで床の高さに持ち上がる**（実際に踏んだ）
  - 当たり判定は床と壁 4 枚を `addSolid(..., 'shop')` で登録し、出るときに
    `hashRemove(bmap, r => r.tile === 'shop')` で外す。48 軒すべてで
    入る→出るを通し、`bstore` 1,991・`bmap` 1,332 が出入りの前後で一致することを実測した
  - 店名の板は**スプライトではなく板メッシュ**にする。`makeLabel()` のスプライトは
    `depthTest: false` なので什器の手前に抜けてしまう（屋外の遠景では利点だが室内では邪魔）
  - 什器は**入口から 1.3m の帯を空ける**。埋めると入った瞬間に棚の中に立つ（実際になった）
  - **大きい什器だけ固体にする**（カウンター・陳列棚・テーブル・机・ATM・冷蔵庫・
    間仕切り・ロッカー）。細い脚や椅子まで固くすると 8.4×6.4m の部屋で引っかかる。
    天端が STEP（0.55m）以内の長椅子などは、登録しても跨げるので入れない
  - **通路は 1.1m 以上要る**（プレイヤーの半径 0.55m の 2 倍）。全幅の棚を 2 列
    並べたら間も両端も通れず、**到達奥行きが 2.7m**（他の分類は 5.4m）になった。
    奥を全幅 1 列、もう 1 列を左半分だけにして、右から奥へ回れるようにしてある
  - 検証は**部屋を 0.3m 格子に切って湧いた場所から幅優先探索**する。
    48 軒すべてで閉じ込め 0、7 分類とも到達奥行き 5.4m（部屋の全長）、
    歩ける面積 16〜29m²
  - 店内では飛行を禁止している（天井を抜けて舞台の外へ出てしまうため）
  - 入れる判定は**扉からの水平距離に加えて高さも見る**（足元が扉の地表 ±2.5m）。
    見ないと屋根の上や飛行中に入れてしまう
- **歩行者**: 取り込んだ歩道網（126 本）の上を **36 人**が歩く。時速 3.6〜5.4km。
  数は**固定**で、165m より遠ざかった人はプレイヤーの手前（30〜130m）へ湧かし直す。
  こうしておくと**世界を広げても人の処理コストが変わらない**。
  胴と頭をそれぞれ 1 つの InstancedMesh にまとめ、per-instance color で
  服と肌の色を振っているので描画は 2 回
- **バス停**: 20 基（うち「城東小学校前」は校門のすぐ前）。支柱と台座は InstancedMesh、
  標識は canvas テクスチャのスプライトにして向きを持たせない。名札が 20 枚も常時
  見えると画面が埋まるので、**135m 以内だけ表示**する
- **シーサーが歩く**: 像だった頃はその場で回っていた。**歩道網の上を四つ足で歩き回り**、
  16m 以内に近づかれると早足になる。ただし早足は **1.45m/s** で、プレイヤーの歩き
  （4.6m/s）よりずっと遅い。**逃げ切らせない**のが狙いで、遊びは「追いつけるか」
  ではなく「曲がり角で回り込めるか」になる。歩調は対角の脚が同時に出る速歩
- **シーサーの造形は Antigravity(agy)に書かせた**。契約（原点=足の裏／前方 -Z／
  体高 1.0〜1.2m／基本ジオメトリのみ／マテリアル使い回し／メッシュ 30 個以内／
  `userData.parts` に可動部を出す）を渡して headless で生成し、こちらで検分して取り込んだ。
  - **可動部の受け渡しを契約に入れるのが要点**。脚は「付け根を原点にした Group」で
    出させたので、`leg.rotation.x` を振るだけで歩く。これが無いと使えない
  - 1 回目は口が読めなかった（シーサーの一番の特徴なのに小さな牙が2本だけ）。
    実機で確認した所見を返して**顔だけ描き直させた**（口の暗がり＋上下 4 本の牙、
    目を正面へ、たてがみを外周のシルエットへ）
  - **blender-mcp は使っていない**。全部が基本形状の世界にスカルプト品を 1 体だけ
    置くと浮くこと、public リポジトリに素性の不確かなモデルを入れたくないこと、
    binary アセットとローダーがゼロの構成を崩したくないことによる
- **ぜんぶ保護したときのアニメーション**: 保護したシーサーは消えているだけなので、
  最後に呼び戻して主役にする。沖縄のシーサーは屋根や門の上から街を見張る守り神なので、
  **集まる → 渦を巻いて頭上へ昇る → 街へ散る**という筋にした（約7.6秒）。
  - **輪のまま昇らせない**のが要点。半径 5.4m の輪だと視野（fov 72°）に 2 体しか
    入らない。いったん**真上へ寄せ集めて「10 体そろった」画をつくる**と、
    足元のリングが重なって花のような形になる
  - 光の柱は探すための目印なので、フィナーレでは消す（10 本が輪になると視界を塞ぐ）
  - 光の粒 170 個は 1 つの InstancedMesh に畳む
  - **店内に居る間は回収しない**。距離は入る前の位置で測っているので、
    店の中に居るあいだにシーサーが表を通ると、最後の 1 体が見えない所で埋まって
    フィナーレが誰にも見られずに終わる
  - 終わったら粒のメッシュを `dispose()` して scene から外す。
    2 回通しで再生して `scene.children` が基準値に戻ることを実測した
- **シーサーの初期配置**: 道路面の重心を候補にし、互いに 110m 以上離して 10 体選ぶ
  （足りなければ 70m → 40m と間隔を緩める）。道沿いに立つので必ず辿り着ける
- **屋根**: 低層の一部を赤瓦色にすると俯瞰したとき一気に沖縄になる
- **当たり判定**: footprint を 24m の空間ハッシュに登録し、近傍セルだけ点-多角形＋
  線分距離で判定。移動は軸ごとに試すので壁ずりが効く。**足元の高さ `y` を渡すと
  建物の天端より上は素通りできる**ので、飛行で屋根を越えられる
- **接地面**: `supportY()` が地表と建物の天端の高い方を返すので、**屋根の上に立てる**
  （縁から出れば落ちる）
- **飛行**: マイクラのクリエイティブ準拠。ジャンプ長押し 320ms で切り替え、
  押している間に1回だけ発火させる（押しっぱなしでも連続トグルしない）。
  重力を切って `vy` を直接指定するので、指を離すとその高度でホバーする
- **地表高さ**: 5m 格子を双一次補間

## スマホ対応

端末の素性は事前に分からないので、**判定できるものは分岐し、分からないものは実測して落とす**方針。

- **端末判定**（`pointer: coarse` か `maxTouchPoints`）で、解像度上限 1.5、影 1024px、
  アンチエイリアス off、地面テクスチャ 1024px（2048px だと 4M ピクセルの JS ループが重い）
- **実測 fps が 40 を切ったら段階的に降格**（影 512px → 解像度等倍 → 影を切る）。
  影を切るときはシェーダを組み直す必要があるので、全マテリアルに `needsUpdate` を通知する。
  `dbg.degrade()` で手動発火できる
- **縦持ちは画角を 72° → 88°** に広げる。Three.js の fov は垂直方向なので、
  そのままだと縦長画面で水平の視野が極端に狭くなる
- 初期の向きは**最も遠くまで開けている方位**（＝街路）を向く。壁を向いて始まると何も見えないため
- `touch-action:none` ＋ `preventDefault` でスワイプによるスクロールと二本指ズームを止め、
  `env(safe-area-inset-*)` でノッチを避ける。開始時に全画面化を試みる（非対応端末では無視される）
- 画面が隠れたら自動ポーズ（着信・ホームに戻ったときに走りっぱなしにしない）

**加工して作成**。PLATEAU のデータは「公共データ利用規約（第1.0版）」（PDL1.0）に準拠し、
CC BY 4.0 と互換。再配布・商用利用とも可能だが、次の3点が条件になる。

1. 出典を明記する（例:「出典：国土交通省 PLATEAUウェブサイト」）
2. 加工した場合はその旨を出典とは別に明記する（例:「…を加工して作成」）
3. 国土交通省が作成したかのような態様で公表しない

このリポジトリでは `public/data/world.json` が加工済みの再配布データにあたるため、
タイトル画面に上記3点を常時表示している（`index.html` の `#card .credit`）。
公開先を変えたり UI を作り替えるときも、この表示は落とさないこと。

**バス停**: [OpenStreetMap](https://www.openstreetmap.org/copyright) contributors
（**ODbL 1.0**）を加工して作成。Overpass API で取得。

> ⚠️ バス停に国土数値情報（P11 バス停留所）を使ってはいけない。
> P11 は「**非商用**」区分で、[利用規約](https://nlftp.mlit.go.jp/ksj/other/agreement_02.html)に
> 「非商用目的のみでの利用（**ただし複製物の再配布を除く**）」と明記されている。
> `world.json` に座標を載せて公開するのは複製物の再配布にあたるため、
> 公開物には使えない。ODbL の OSM ならクレジットと継承を守れば再配布できる。
> なお ODbL は派生データベースに継承を要求するので、`world.json` のバス停部分は
> ODbL 扱いになる。
